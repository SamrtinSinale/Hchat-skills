# Hchat 移植 playbook（把一句话变成一次完整交付）

用户只说一句“把旧版 Hchat 功能移植到新版”时，按本文件自动补齐其余输入，**不要反过来让用户逐项交代**。

## 默认约定（先说清假设，再动手）

- 工作目录：`/storage/emulated/0/Hchat工作目录/`，Linux 环境里就是 `/storage/emulated/0/Hchat工作目录/`。
- 命名惯例：`Hchat-release-signed*.apk`（官方新版）、`Hchat_<版本>.apk`（带补丁的旧版）、
  `Hchat_*_patched_unsigned.apk`（历史产物，**不要当对照**）。
- 解包工作区：`/workspace/hchat-compare-<随机>/`，每个版本一对 `A_decoded/`（新版）、`B_decoded/`（旧版）。
- 输出：`/workspace/Hchat_<新版>_eta_<用途>_unsigned.apk`，再复制回工作目录。

## 自动发现顺序

1. `ls -la /storage/emulated/0/Hchat工作目录/`，对每个 APK 解出 `classes.dex` 里的版本字符串
   （`模块版本: x.y.z (nnn)`）与是否含 `customnotify/Eta*` 类，得到“版本 → 有无补丁”表。
2. 取**最高版本且无补丁**的包作为新版（A），**最高版本且带补丁**的包作为旧版（B）。
3. 找 B 的同版本干净对照：优先在历史目录里找（`diff -rq` 只有 `Eta*` 类差异即命中）；
   找不到就问用户一句“有没有 6.x.x 的原版包”，**不要**默认用别的版本当对照。

## 必须回头问用户的三种情况

- 工作目录里没有旧版带补丁的包，或没有新版官方包。
- 找不到同版本的干净对照（补丁集可能不全，要用户确认是否接受）。
- 多个候选包版本相同、无法判断哪个是官方、哪个是二次修改。

其余情况（选哪个包、输出叫什么、用哪个工作区）自己决定，做完在交付说明里写清假设。

## 交付模板（固定四段）

1. **产物**：路径、APK sha256、`classes.dex` sha256、只替换了哪些 zip 条目。
2. **搬了什么**：逐条对应上表，写“落点 + 校验方式”。
3. **有意没搬 / 偏离原版**：写清原因，以及“要的话我再单独做”。
4. **你要验证的**：未实跑；列出 2–4 个具体动作让用户测。产物不带签名是常态，本机可直接安装，别写成待办（只有要分发给他人时才提签名）。
