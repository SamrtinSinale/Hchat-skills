# 案例：Hchat 6.3.8 定制补丁 → 6.4.7（微信增强模块）

一次完整移植的实录，包含一次线上事故的复盘。移植对象是 LSPosed 模块 `h.Hchat`：
旧版 6.3.8 带第三方定制补丁，新版 6.4.7 是官方新版，目标是把 6.3.8 的定制逐条搬过去。

## 1. 补丁集是怎么枚举出来的

必须有干净的 6.3.8 解码树（`hchat_638_full`，无 `Eta*` 类）当对照，然后
`diff -rq 干净/smali 定制/smali`：

- 定制新增类：13 个 `h/Hchat/hooks/items/customnotify/Eta*.smali`
- 改动过的框架类：15 个（aj6、bn6、h53、ip3、ki2、mm4、pw0、r76、tl、ui6、uw0、vi4、x7、yk0、z74）
- 其中 **4 个是重打包产物**（aj6/r76/ui6 只是字段初值写法 `= false` → 空；x7 是 try 块边界），不是补丁

真补丁归为 6 类：`setSmallIcon` 接管（7 个类 8 处）、`EtaChatClear` 注入、设置页两行入口、
行点击分发、快速已读一行、通知文字格式（`cln` + `[N条]`→`[N]` + `[N]` 追加行）、设置搜索索引。

## 3. 事故：覆盖了长生命周期寄存器 v15

**现象**：装上移植版后，通知栏的「标为已读」「快捷回复」点了没反应。

**排查**：
- `logcat -b all | grep notification_action_clicked` 显示广播确实发出去了，
  通知本身 `actions=2`，Intent 也 `(has extras)` → 按钮在、广播发了，是对面收不到。
- 回到 6.4.7 的 `y21`，统计 `v15` 的出现：**只在 9403 行写了一次**
  `const-string v15, "hchat_custom_notification_talker"`，之后 9516、10315、10811、
  11068、11380、11860 全是**读**——通知 extras 写入、两个动作 Intent 的 `putExtra` 都用它当键名。
- 我照搬 6.3.8 的两段代码时用了 `v15` 当临时寄存器，把键名覆盖成了消息标题和 `"]"`。

**为什么照抄会出事**：6.3.8 里那个位置 `v15` 是空闲的——旧版作者在每个使用点前都重新
`const-string v15, "…_talker"` 设一遍，所以照抄安全；6.4.7 只在开头设一次、后面长期复用。

**修复**：换成插入点确实空闲的寄存器（`v2`、`v14`、`v9`），先用 `reg_free.py` 证明空闲再落补丁。

## 4. 其它踩到的坑

- **标签重名**：新加的 `:cond_b` 与该方法已有标签冲突，汇编直接失败 → 改名 `:cond_40`。
- **寄存器越界**：`invoke-virtual {v21, v23}` 报
  `Invalid register: v21. Must be between v0 and v15, inclusive.`
  —— 35c 形式只能 v0–v15，要更高寄存器得用 `/range`。
- **有意偏离原版**：内联文本裁剪加了 `if-eqz v10, :cond_xxx` 空值守卫，原版这里会 NPE。

## 5. 交付时的验证清单（本次实际做的）

- 汇编 `ok=9408 fail=0`
- `apktool d -r` 反解成品通过，9408 类、14 个 `Eta*` 类、8 处 `apply` 接管点都在
- 与上一版解码树 `diff -rq`：只有 `y21`/`u21`/`in3` 三个类不同
- `dex2oat --compiler-filter=verify` 无报错
- 记录 APK 与 `classes.dex` 的 sha256，并复制到用户指定目录
- 明确告知：**未签名**、未在设备实跑，需要用户验证「标为已读 / 快捷回复 / 进聊天清通知」
